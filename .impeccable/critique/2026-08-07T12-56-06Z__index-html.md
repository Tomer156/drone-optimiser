## Design Specificity Verdict

The advisory engine carries two copy registers with a rule that Auto may only name what Auto can change. What is generic is the shell: an eight-card flat grid, a 56px toolbar, a donut with a legend. ## Overall Impression

The engine and the language are genuinely good; the entry point is broken. Every measurement in this review is worse than it needs to be because of one line of state: the app boots into **Pro mode at step 3** with nothing built, which hides the primary action, opens the densest surface first, and makes the only on-screen instruction false. Fix that line and the score moves several points without touching a single component.

The single biggest opportunity: **the app already knows enough to answer on first paint.** It has the mission, the mass budget and the goal, and it already renders a Layout card and a mass donut from a default motor. It is doing the arithmetic either way. Running the sweep on mount would turn the product's moment from *waiting* into *reacting*.

## What's Working

**The Required vs selected table.** Six rows, four columns, one line per demand. It removes the arithmetic step: "Hover thrust / motor · 362 g · 919 g · 2.5×" answers *is this enough* without holding 362 in your head. Tabular mono at a fixed 13px means a shortfall is visible as a shape before it is read as a number.

**The advisory engine.** Three correct decisions stacked: findings sorted worst-first so severity is positional not just chromatic; each finding carries a step and clicking it navigates there, so the diagnosis *is* the fix path; and two copy registers with an explicit rule that Auto may only name what Auto can change — it even suppresses "Motor over-specced" in Auto because a user who cannot see the motor list cannot act on it.

**Colour discipline and the dark theme.** 182 text nodes checked per theme, **zero contrast failures in either** (worst: 5.16:1 light, 4.58:1 dark). Dark mode is a separate ramp, not an inversion. Chroma appears only on fit status.

## Priority Issues

### [P0] The app boots into Pro mode at step 3, where the primary action does not exist

**What.** `state = { mode:'pro', step:3, … built:false }`. Verified live: fresh load reports Pro, the Design flags panel says *"No build yet — Pick a motor and pack, or hit Optimise"*, and the Optimise button computes to `display: none` (`optDisplay: pro ? 'none' : 'flex'`). Visible buttons on first paint: Back, Next, Reset, Export. The gate modal that is meant to sell Pro is never seen because the user is already inside it.

**Why it matters.** This is the entire first impression of an Operate surface, and it fails three ways at once: densest mode first, primary action invisible, only instruction wrong. Cognitive load, the emotional valley and discoverability are all downstream of it.

**Fix.** `mode:'auto', step:1`. That one change restores the Optimise button, collapses the catalogue, makes the gate reachable and makes the copy true. Then run the sweep once on mount so the first frame shows a real build instead of six em-dashes.

**Suggested command:** `/impeccable onboard`

### [P1] The build cannot leave the tab, and Export is a dead button

**What.** No `localStorage`, no `sessionStorage`, no URL state. The Export button carries an icon and a label and **no `onClick` attribute** — confirmed at index.html:455; the Reset button beside it has `onClick="{{ reset }}"`. No CSV, Blob or download code exists anywhere in the file. Reset wipes everything with no confirmation.

**Why it matters.** The product's output is a parts list someone takes to a shop. It currently cannot leave the browser tab. A dead button labelled Export is worse than no button: it advertises a capability and silently does nothing.

**Fix.** Serialise the eleven state fields into the URL hash — that buys persistence, sharing and back-button undo from one mechanism. Wire Export to emit the Selected components list plus the comparison table. Confirm on Reset.

**Suggested command:** `/impeccable harden`

### [P1] 5.2 seconds of frozen window at the highest-stakes moment

**What.** Measured on a cold load: **5,191 ms**, 46,115 bench interpolations, main thread blocked. The button is not `disabled` during it (`disabled: false`, `aria-busy: "false"` after settle), so a second click queues a second sweep. No `aria-live`, so a screen-reader user gets no signal that 83 numbers changed. **DESIGN.md records "roughly 200 ms" — that was my own warm-cache measurement and it is wrong by 25×.**

**Why it matters.** The product's whole promise compressed into one press, delivered as a hang. A frozen interface reads as crashed, not as working hard.

**Fix.** Set `disabled` while optimising (the flag exists). Replace the static label with the count the sweep already knows. Add a polite `aria-live` for the result line. Chunk the sweep across frames if a real progress bar is wanted. Correct the DESIGN.md figure.

**Suggested command:** `/impeccable optimize`

### [P1] The keyboard and screen-reader path is broken in four specific places

**What.** Measured: **one heading in the whole app** (the h1; no h2–h6, so ten panel titles are unnavigable 13px spans). **Zero `aria-pressed`/`aria-selected`/`aria-expanded`** anywhere — Auto/Pro, four flight-style chips, three goal chips and six step headers express state through colour alone. `role="tablist"` contains **zero `role="tab"`**. The Pro gate modal has no `role="dialog"`, no `aria-modal`, focus is never moved into it, and **Escape does not close it** — and it is the only route to Pro. Separately, **15 of 19 tooltips sit on non-focusable divs**, so the plain-language explanations are mouse-only.

**Why it matters.** Enter/Space activation and focus rings were done properly in an earlier pass; this is the layer above that, and without it the work already done is not reachable.

**Fix.** Promote panel titles to `h2`. Add `aria-pressed` to the toggle chips and `aria-expanded` to step headers. Make the tablist real or drop the role. Give the modal `role="dialog"`, `aria-modal`, initial focus and Escape. Add `tabindex="0"` to tooltip hosts.

**Suggested command:** `/impeccable audit`

### [P2] The most original control in the app encodes its signal at 1.06:1

**What.** Each slider track carries a computed fit gradient from `TINT = {good:'#BFE0CB', med:'#F0DCAE', bad:'#F0C9C1'}`. Adjacent-zone contrast measured at **good vs med 1.06:1, good vs bad 1.07:1, med vs bad 1.12:1**, on a track rendered **4px tall**, with no legend anywhere. DESIGN.md's own rule requires 3:1 for graphics.

**Why it matters.** Forty physics evaluations per track, nine tracks per render, spent on a signal nobody can see or decode. This is the idea that separates the tool from a spreadsheet.

**Fix.** Use the saturated `PAL` values at reduced alpha so adjacent zones clear 3:1; raise the track to 6px with a 24px padded hit area (it is currently 4px tall, failing WCAG 2.5.8 along with nine other sliders); add one tooltip explaining the colours.

**Suggested command:** `/impeccable colorize`

### [P2] Empty-state incoherence, and empty tooltips paint black blobs

**What.** With `built:false`, five panels correctly show a null state while **Take-off mass** renders a full 1.52 kg five-segment donut and **Layout** specifies "Prop size 9″ · 472 mm · Diagonal M–M 345 · Tip-to-tip 573" — a complete frame spec for a drone with no motor. Separately, five comparison rows carry `data-tip=""`, and because the rule is `[data-tip]:hover::after { content: attr(data-tip); padding: 9px 11px }`, hovering paints **an empty black pill over the row below** (reproduced on the Capacity row, obscuring C-rating).

**Fix.** Gate Layout and Take-off mass on `built`, or label them "from your estimate". Change the selector to `[data-tip]:not([data-tip=""])`.

**Suggested command:** `/impeccable polish`

## Persona Red Flags

**Alex (power user)** — The Prop + Motor list is **321 rows, alphabetical, no search, no sort**; the first three visible rows are all flagged "current ratio outside band", so the catalogue's worst options lead. Rows display g/W and throttle but cannot be sorted by either. No A/B comparison: clicking a second motor replaces the first, so comparing two candidates means clicking back and reading eight cards from memory. Export is inert and there is no URL state, so nothing can be saved or sent. Each Optimise costs 5.2 s frozen and the button stays enabled — iterating the three goals costs 15 s of hang, doubled by any impatient double-click. **Pro shows him less than Auto:** it replaces Selected components, so the ESC rating, AWG gauge and connector — the four facts needed to order parts — are beginner-mode only.

**Sam (accessibility-dependent)** — Ten sliders render **243×4 px** against a 24×24 minimum. **One heading** in the application. **Zero** `aria-pressed`/`aria-selected`/`aria-expanded`, so no toggle state is announced. `role="tablist"` with zero tabs. **Zero `aria-live`**, so a sweep that rewrites 83 numbers is silent. 15 of 19 tooltips keyboard-unreachable, including all six comparison-row explanations. The gate modal has no dialog semantics, never receives focus, and cannot be dismissed with Escape. The donut responds to `onMouseEnter` only, with no keyboard equivalent. Every size is an inline `px` inside a `100vh; overflow:hidden` shell, so OS text scaling has no effect.

## Minor Observations

- **1366×768 overflows by 18 px** with the charts already at their floor — enough to look broken, not enough to look scrollable.
- **No responsive design.** One `@media` in the file and it is `@media print` inside the vendored runtime. At 375px the sidebar takes 77% of the width.
- **"XT90 connector · 352 A worst case"** — the connector is read from the pack record and never checked against the current the app just computed.
- **`prefers-color-scheme` and `prefers-reduced-motion` are never read**; theme is not persisted.
- **The Prop field in Selected components renders blank** for the 79 size-only entries, leaving the reserved 33px as a visible hole.
- **Auto mode disables its own accordion** — all four sections are force-expanded, so the numbered step headers are clickable but do nothing.
- **13 decorative SVGs** are neither `role="img"`+labelled nor `aria-hidden="true"`.
- **The sidebar scrolls 53 px at 1280×860** and 213 px at 1280×700 — expected for a long form, but it is the region a first-time user reads first.

## Questions to Consider

1. **If the sweep can produce a complete build in one press, why is pressing it the user's job?** The app has everything it needs on first paint and is doing the arithmetic anyway. If the answer simply appeared and the button became "Re-optimise", the moment moves from waiting to reacting.
2. **What does Pro actually give a user that Auto doesn't, besides more work?** It removes the Optimise button, removes the only card you can take to a shop, and adds a 321-row alphabetical list — and it is the default, behind a gate that sells nothing.
3. **The Status-Only Rule says colour means fit — so why is the one place the app computes fit across a whole range rendered in three pastels 1.06:1 apart with no legend?** At what point does a rule protecting the palette stop the product saying what it knows?
